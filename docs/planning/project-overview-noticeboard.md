## 為什麼要改

現在的 Overview 來自 enterprise-parity 計畫,所以它報告的是**商業版 Plane 報告的東西** ——
六塊並排的資料,沒有回答任何一個具體問題。

它要服務的其實是兩種人,而兩種人問的是同一串問題:

| 誰       | 問什麼                                      |
| -------- | ------------------------------------------- |
| 管理階層 | 產品開發到哪了?什麼時候能出貨?              |
| 產品經理 | 推進有沒有在規劃上?客戶在抱怨什麼,接住了沒? |

還有一條**跨職能**的要求:前線業務導入時,客戶反映的抱怨要能及時傳到工程團隊。
所以這頁不能只有工程項目 —— 市場、商務、客戶緊急事件都要有位置。

## 設計原則:三類資料,三種互動規則

這是整份規格的骨幹。每一個區塊都必須先歸類,才能決定它長什麼樣。

| 類別       | 定義                    | 互動規則                       | 為什麼                             |
| ---------- | ----------------------- | ------------------------------ | ---------------------------------- |
| **A 衍生** | 從別的資料算出來        | **不可在此編輯**,只能點進源頭  | 讓人改算出來的數字等於製造兩個真相 |
| **B 分流** | 記錄已存在,人改它的狀態 | **一個動作**,不是表單          | 是狀態轉移,不是重新輸入            |
| **C 原創** | 人在這裡產生第一手內容  | **完整 CRUD**:發布、編輯、刪除 | 這裡就是它的家                     |

違反這條規則的設計會出現的症狀:算出來的數字旁邊放一個可編輯欄位,兩者永遠可以互相矛盾
而沒有人負責。現在的 Properties 面板就是這樣被拿掉的。

## 逐區塊:讀哪來、誰寫、寫去哪

| 區塊          | 類  | 讀                                   | 寫                                | 狀態 |
| ------------- | --- | ------------------------------------ | --------------------------------- | ---- |
| 出貨判定      | A   | `testing/overview` 的 `release_gate` | 無                                | ✅   |
| 進度 / 里程碑 | A   | `overview`                           | 無                                | ✅   |
| 需要注意      | A   | `attention/`                         | 無(點進工作項改)                  | ✅   |
| 客戶前線      | B   | `frontline/`                         | `PATCH intake-issues/<issue_id>/` | ✅   |
| 客戶標記      | B   | `WorkItemPropertyValue`              | `work-item-property-values`       | ✅   |
| 公佈欄        | C   | `EntityUpdate`                       | POST / PATCH / DELETE             | ✅   |
| 會議紀錄      | C   | Pages                                | Pages 全套                        | ✅   |

**API 的寫入路徑幾乎都在**,缺的是 UI 與兩個欄位(見下)。

一個實作時才確認的細節:`PATCH intake-issues/<id>/` 的 `<id>` 是**工作項的 id**,
不是 intake 列的 id —— 端點自己是用 `issue_id` 反查的。傳錯會拿到 404,
讀起來像權限問題。所以 `frontline/` 兩個 id 都回。

## 需要的 schema 變更

規劃時預期只有一項。實作到階段二才發現第二項:**面板要能找到「客戶」這個屬性**。
屬性由使用者自己建立,名字可能叫客戶、租戶、地區或試點批次 —— 程式不能猜。
所以需要一個地方記下「使用者選了哪一個」,否則「做成活的」只做了一半:
欄位是活的,但沒有人告訴畫面要讀哪一欄。

解法是 `WorkItemProperty.is_grouping_dimension`,每專案至多一個,只允許 select 類型
(用自由文字分組會每個錯字生一組)。**選擇本身是資料,存在專案層**,不是每個閱讀者
各自的偏好 —— 大家看的應該是同一塊板子。

### 公佈欄分類 → 掛 Label,不要新 enum

`EntityUpdate.status` 只有 `on_track / at_risk / off_track`,那是**專案健康度**不是主題分類,
不能挪用。

分類必須是**活的** —— 使用者自己增刪,像 Notion。`Label` 已經滿足:每專案獨立、有顏色、
有階層(`parent`)、設定頁現成。

所以只加一張 join table:

```
EntityUpdateLabel(entity_update, label, project, workspace)
```

**結構動一次 migration,分類值永遠由使用者決定。** 沒有任何分類名稱寫進程式碼。

### 客戶 → 用既有的 WorkItemProperty,零 migration

`WorkItemProperty` 已經支援 7 種型別、可綁定特定 work item type、可設必填與預設值。
建三個屬性即可,全部透過現有設定頁:

| 屬性       | 型別                             | 它改變什麼決定                        |
| ---------- | -------------------------------- | ------------------------------------- |
| 客戶       | `multi_select`                   | 哪個客戶在抱怨 → 分組、看單一客戶全貌 |
| 導入階段   | `select`:POC / 試營運 / 正式上線 | 同一個 bug,正式上線客戶回報的先修     |
| 客戶承諾日 | `date`                           | **已存在**;有無對外承諾 → 排程硬約束  |

綁在 Bug 與 Intake 相關的 type 上,不要綁全部 —— 內部技術債不該被問哪個客戶。

專案層而非 workspace 層:專案彼此獨立,同一個客戶若跨專案合作就各自建立。等到跨專案
查詢真的變成需求,再升級成 workspace 實體,那時才會知道要存什麼欄位。

## 實作時偏離規格之處

- **`show all` 之後的分類篩選在前端做**。板子只有十則,為了隱藏兩則多跑一次
  round trip 比點擊本身還慢。端點仍支援 `?label=`,給未來的分頁用。
- **客戶屬性沒有預先建立**。規格寫「建三個屬性(設定頁操作)」,實作改成
  什麼都不預設 —— 預先建立等於替使用者決定他的客戶叫什麼,正是這份規格要避免的。
- **前線面板沒有渲染其他屬性(導入階段、承諾日)的 chip**。列表已有五個欄位,
  再加兩個 chip 會讓一行讀不完。點進工作項就看得到。

## 不做什麼

- **不做跨專案客戶視圖**。專案獨立是前提;跨專案是另一個頁面,等這個模式證明有用再說。
- **不加 CRM 欄位**(聯絡人、合約金額、產業別)。它們不會改變工程接下來做什麼。
  沒人填的欄位比沒有欄位更糟,因為它看起來像資料。
- **不讓 A 類區塊可編輯**。要改就點進源頭改。

## 驗收

- 公佈欄:發布、編輯、刪除、回覆、依分類篩選;非作者非 ADMIN 看不到編輯入口
- 客戶前線:標了客戶的 Intake 會分組;一鍵把待處理改成已排入,列表即時反映
- 需要注意:逾期與緊急各自出現,點擊進入該工作項
- 沒有測試資料的專案不顯示出貨判定;沒有 Intake 的專案不顯示客戶前線

自動化的部分在 `apps/api/plane/tests/contract/app/` 兩個檔案共 24 個測試:
`test_noticeboard.py`(發布 / 改稿 / 歸檔 / 撤下 / 跨專案標籤拒絕 / 權限邊界)、
`test_frontline_and_attention.py`(分組 / 多值同時歸屬多組 / 未歸屬不隱藏 /
五種狀態收斂成三種 / 上限與其回報 / 選項被改名仍渲染 / 逾期優先 / 已完成排除 /
同一筆不重複 / 最舊優先 / 指派人)。

## 怎麼開始用

1. 專案設定 → 自訂屬性,建一個 select 或 multi-select,名字自己取(客戶、租戶、地區)
2. 同一列點「Group overview by this」
3. 在 Intake 的工作項上填那個屬性
4. Overview 出現該面板,標題就是你取的名字

公佈欄的分類同理:專案設定 → 標籤,建幾個自己的分類,發公告時勾選。
兩者都沒有預設值 —— 預設值等於替你決定你的客戶叫什麼。
