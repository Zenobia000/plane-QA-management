# Intake:讓進件在當下就能歸屬

> 狀態:**已實作,待瀏覽器驗收** · 2026-08-07
> 前身:[`project-overview-noticeboard.md`](project-overview-noticeboard.md) 階段二(客戶前線)
> 這份文件補的是那一階段留下的缺口:面板會分組,但沒有任何 UI 能填分組的值。

## 為什麼要做

`project-overview-noticeboard.md` 的「怎麼開始用」第 3 步寫著「在 Intake 的工作項上填那個屬性」。
**這一步在 UI 上做不到。** Intake 的建立視窗與詳情頁都沒有渲染自訂屬性,所以凡是從 UI
進來的進件全部落在客戶前線面板的「未歸屬」堆裡。demo 專案那三家客戶有名字,是 seed
直接寫資料庫的,不是任何人點出來的。

面板本身沒問題,缺的是輸入端。

## 用戶旅程與落差

| #   | 角色                   | 他在做什麼                               | 他知道什麼             | 現況擋住他的地方                                                          |
| :-- | :--------------------- | :--------------------------------------- | :--------------------- | :------------------------------------------------------------------------ |
| 1   | 前線回報者(業務/客服)  | 接到客戶電話,開 Intake 建一筆            | 哪個客戶、痛在哪、多急 | 表單第一個問他 **State**(只有一個選項、送出後端還會覆寫);**完全不問客戶** |
| 2   | 分流者(PM)             | 每天掃 Intake Open,判斷後 Accept/Decline | 這筆該歸誰、要不要做   | 詳情頁沒有客戶欄位,補不了;想標客戶得先 Accept 再跳到 Work items 開同一筆  |
| 3   | Overview 讀者(主管/PM) | 看哪個客戶在抱怨、接住了沒               | —                      | 全部落在「未歸屬」,面板等於沒作用                                         |

一句話:**表單問了回報者沒有答案的問題,沒問他唯一有答案的問題。**

旅程 2 那條「先 Accept 再跳頁補標」特別有害 —— 它逼分流者為了填一個欄位而先做出
分流決定,順序反了。

## 決策

三個決定,由產品 owner 於 2026-08-07 拍板。

### DEC-IA-1 建立表單問客戶,但只對 MEMBER 以上顯示

進件建立(`IntakeIssueViewSet.create`)允許 GUEST;寫屬性值
(`WorkItemPropertyValueDetailEndpoint`,`ProjectEntityPermission`)要 MEMBER 以上。
兩者權限不一致。

**顯示一個註定 403 的欄位,比沒有欄位更糟** —— 使用者會以為填了,結果沒存。
所以欄位只對寫得進去的人出現;GUEST 回報的進件由分流者在詳情頁補標(旅程 2)。

未採用「擴充 API 讓 GUEST 連同進件一起寫」:那要動權限邊界,風險與範圍都超過這個切片。
若日後 GUEST 回報成為主要來源,再回頭做。

### DEC-IA-2 建立表單只放分組維度,詳情頁放全部

兩種角色知道的東西不一樣:前線只知道「這是誰報的」,分流者知道其餘。
表單問他答得出來的,詳情頁給分流者補齊。

「分組維度」是專案自己標的屬性(`is_grouping_dimension`),名字由專案決定 ——
本 repo 的 demo 叫「合作客戶」,別的專案可能叫租戶或地區。
**程式不認得任何一個名字**,這條在 `project-overview-noticeboard.md` 已經定案,這裡沿用。

### DEC-IA-3 移除建立表單的狀態控制項

`IntakeIssueViewSet.create` 無條件執行 `request.data["issue"]["state_id"] = triage_state.id`。
不論表單送什麼,後端都覆寫成 Triage。**那個下拉從第一天起就是空轉的**,
打開只有一個選項、選了也不算數。

留著它等於在表單上放一個假問題。詳情頁的狀態欄則保留(唯讀),但要顯示真正的狀態名。

## BDD 場景

### Feature: 進件在建立當下就能歸屬

```gherkin
場景: SCN-IA-01 有分組維度的專案,表單問這一個欄位
  假設 專案有一個標記為 Overview 分組維度、且未綁定工作項目類型的屬性
  且 我在這個專案是 MEMBER
  當 我開啟「建立進件工作項目」
  那麼 表單上出現該屬性的欄位,標題就是該屬性的名字
  且 表單上沒有狀態(Triage)控制項

場景: SCN-IA-02 選了值就歸屬,Overview 立刻反映
  假設 分組維度是多選屬性「合作客戶」,選項含「Acme 物流」
  當 我填標題、選「Acme 物流」並建立
  那麼 該進件的「合作客戶」值為 Acme 物流
  且 客戶前線面板把它列在「Acme 物流」而不是「未歸屬」

場景: SCN-IA-03 GUEST 看不到一個他存不進去的欄位
  假設 我在這個專案是 GUEST
  當 我開啟建立進件視窗
  那麼 表單上沒有任何自訂屬性欄位
  且 我仍然可以建立進件

場景: SCN-IA-04 沒有標分組維度的專案,表單不長出欄位
  假設 專案沒有任何屬性被標為分組維度
  當 我開啟建立進件視窗
  那麼 表單上沒有任何自訂屬性欄位

場景: SCN-IA-05 分組維度被綁到某個工作項目類型時不顯示
  假設 分組維度屬性被綁定到「Bug」類型
  當 我開啟建立進件視窗
  那麼 表單上沒有該欄位
  # 進件建立的工作項沒有類型,後端 WorkItemPropertyValueDetailEndpoint 會拒絕這個寫入。
  # 表單不該問一個送出去必被退回的值。

場景: SCN-IA-06 屬性是必填而未填時,擋在送出前
  假設 分組維度屬性設為必填
  當 我沒有選值就按建立
  那麼 該欄位顯示必填錯誤
  且 進件沒有被建立

場景: SCN-IA-07 屬性寫入失敗不得回報成功
  假設 我在建立視窗選了「Acme 物流」
  當 進件建立成功但屬性寫入失敗
  那麼 訊息說明進件已建立、但該屬性未儲存
  且 不顯示一般的成功訊息
```

### Feature: 分流時看得見狀態、補得了歸屬

```gherkin
場景: SCN-IA-08 詳情頁顯示真正的狀態名
  假設 一筆待處理的進件
  當 我開啟它
  那麼 狀態欄顯示「Triage」,不是佔位字「State」
  且 它不呈現可點擊的下拉外觀

場景: SCN-IA-09 分流者可以在詳情頁補標
  假設 我對這筆進件有編輯權,且我在專案是 MEMBER 以上
  當 我在詳情頁選了分組維度的值
  那麼 值即時儲存
  且 客戶前線面板把它移出「未歸屬」

場景: SCN-IA-10 詳情頁顯示全部未綁類型的自訂屬性
  假設 專案有三個未綁定類型的自訂屬性,其中一個是分組維度
  當 我開啟進件詳情頁
  那麼 三個欄位都出現
  # DEC-IA-2:建立表單只問一個,詳情頁補齊其餘。

場景: SCN-IA-11 沒有編輯權時屬性唯讀
  假設 我不是專案 ADMIN,也不是這筆進件的建立者
  那麼 詳情頁的自訂屬性呈現唯讀,與同一面板的其他欄位一致
  # 沿用 Intake 詳情頁既有的 isEditable 規則(ADMIN 或建立者),不另立一套。
```

## 不做什麼

- **不改 Intake 詳情頁的編輯權規則**。現行是 ADMIN 或建立者,自訂屬性沿用同一條,
  不為了讓 MEMBER 分流者能編輯而在這裡開特例 —— 那是另一個決定,要動就整個面板一起動。
- **不擴充進件建立 API 收屬性值**。見 DEC-IA-1。
- **不改 `create_more` 的共用文案**。那個開關本身沒有缺陷(它只影響送出後的行為),
  改文案會波及一般工作項目視窗。
