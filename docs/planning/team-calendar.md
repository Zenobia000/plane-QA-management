# 團隊行事曆:讓遠端的時間變成可以排的東西

> 狀態:**規劃中** · 2026-08-06
> 前身:ADR 0008(聚合邊界、宣告而非觀測、分配模型)
> 交付:`docs/planning/team-calendar-wbs.md`

## 為什麼要做

團隊多半遠端,而且一個人同時在好幾個專案上。這產生三個問題,而它們不是同一個問題:

| #   | 問題                          | 原話                                             | 現在的答案                  |
| --- | ----------------------------- | ------------------------------------------------ | --------------------------- |
| 1   | 什麼時候找得到人一起討論?     | 「確保找得到人時上線討論」                       | 猜,或在群組裡喊             |
| 2   | 誰哪幾天不在?                 | 「管理請假 事件等事宜」                          | 沒有紀錄                    |
| 3   | 一個人的時間怎麼分給多個專案? | 「每個帳號的時間和假不知道怎麼呈現和分配比較好」 | 每個專案都當自己擁有他 100% |

第 3 個問題是前兩個的乘數。三個專案各自排程時都假設 Ana 全職在自己這邊,加起來就是 300% 的
Ana。這不是估計不準,是三份計畫各自內部一致、彼此矛盾,而且沒有任何一個畫面會顯示這件事。

Cycle 有 `start_date` 和 `end_date`,但沒有任何「可用工時」的概念。排程建立在「每個人每天都在、
而且只在這裡」的假設上,這個假設每個月都會被請假、國定假日、跨專案切換打破。

## 設計原則一:宣告,不是觀測

**目的不是微管理。** 這條不是免責聲明,是設計約束——它直接刪掉了一整類本來最省事的做法。

| 界線             | 不做什麼                                            | 為什麼                                                                                                         |
| ---------------- | --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| **無在線偵測**   | 沒有心跳、沒有上線燈號、沒有「最後活躍」            | `User.last_active` 存在於 model,本模組**規定不得讀取或輸出**。契約測試會斷言任何 availability 回應都不含此欄位 |
| **無個人歷史**   | 沒有「Ana 今年請了 12 天」的畫面                    | 這也是本輪不做額度的原因——餘額就是個人請假的累計值,是意圖漂移時第一個被拿來用的東西                            |
| **產能只朝前看** | Cycle 面板只回答「排不排得下」,不報告「做了幾小時」 | 產能是規劃輸入,不是績效紀錄。以 cycle 為單位計算,不跨時間累積到個人身上                                        |
| **粒度停在半天** | 不能登記「14:00–15:30 不在」                        | 更細就變成工時表。半天是讓算術精確、日曆畫得出來的那個單位                                                     |

這是 ADR 0007「資料夾是宣告的,不是推論的」同一個動作,套用在人身上。**對文件推論狀態是 bug;
對人推論狀態是監控。**

代價要說清楚:宣告可能是錯的。忘記登記休假的人在系統裡看起來找得到。替代方案是觀測,而那正是
被排除的東西——這個取捨是刻意的,不是疏漏。

## 設計原則二:一個人有三種「時間」,不能混為一談

這是回答「不知道怎麼呈現」的骨幹。三種時間各有自己的資料、自己的畫面、自己的互動規則。

| 種類         | 是什麼                         | 存在哪                                   | 誰能改              |
| ------------ | ------------------------------ | ---------------------------------------- | ------------------- |
| **可及時段** | 這個人一天當中幾點到幾點找得到 | `MemberWorkProfile` 的工作時段與核心時段 | 本人;管理員可代設   |
| **缺席**     | 這幾天(或半天)整個人不在       | `MemberLeave`、`TeamEvent`               | 本人申請,核准人決定 |
| **分配**     | 這個人的產能怎麼切給各專案     | `MemberProjectAllocation` 的百分比       | 只有管理員          |

把三者塞進同一個畫面是這類產品最常見的失敗:請假表單裡冒出專案下拉選單,於是「請假」變成
「跟這個專案請假」,而人並不是跟專案請假的。**缺席屬於人,分配屬於專案與人的關係。**

## 版面:一個 workspace 頁面,三個分頁

路徑 `/[workspaceSlug]/calendar/`,分頁殼比照 testing 模組的形狀。

### 分頁一「時段」——預設落地頁,回答問題 1

週視圖,所有人畫在**同一條時間軸**上,軸的時區是看的人自己的。這是遠端團隊每天會打開的那一頁。

```
┌─ 時段 ─┬─ 假期 ─┬─ 分配 ─┐        時區 [Asia/Taipei ▾]   ‹ 8/10–8/16 ›
└────────┴────────┴────────┘

              08  10  12  14  16  18  20  22
Ana  台北     ····████████░░████████············    ░ 午休   █ 工作
              09:00–18:00 · 核心 14:00–17:00

Bob  柏林     ················████████████████··
              15:00–24:00 (當地 09:00–18:00)

Cara 台北     ▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒    ▒ 特休(整天)

──────────────────────────────────────────────
共同可及      ················██████············
              15:00–18:00 · 2 人(Cara 休假)

                                    [ 找共同時段 ]
```

- 「核心時段」畫得比工作時段深。**「我 09:00–18:00 上班」和「這段時間都可以抓我」是兩件不同的
  宣告**,把它們畫成同一個顏色,日曆就會開始被不信任。
- 底部那條共同可及是算出來的(A 類衍生資料),不可編輯,點下去展開是誰造成缺口。
- 缺席的人整條變灰,不是消失。**看得到「Cara 今天不在」比看不到她這一列更有用。**
- 「找共同時段」輸入參與者與時長,回傳未來幾天內足夠長的重疊窗口,依看的人的時區呈現。

### 分頁二「假期」——回答問題 2

月曆色塊牆。市面上這類產品被天天打開的唯一畫面就是這個,所以它要簡單到不需要說明。

```
┌─ 時段 ─┬─ 假期 ─┬─ 分配 ─┐    ‹ 2026 年 8 月 ›   [ 登記請假 ]

        一   二   三   四   五   六   日
        3    4    5    6    7    8    9
Ana          ███████████
Bob                    ▓▓▓▓▓
Cara                        ◐

        10   11   12   13   14   15   16
Ana
Bob                              ⬛ 全員教育訓練 ⬛
Cara    ███████████████

███ 特休   ▓▓▓ 病假   ◐ 半天   ⬛ 團隊事件
```

- 只有本人、指定核准人、管理員看得到事由。**其他人看到的是假別與日期,沒有原因。**
  這條寫在 serializer 而不是前端——API 回傳的欄位就是公開的,不管哪個元件決定不畫它。
- 補班日在月曆上標出來(台灣特有:週六卻算工作日),否則天數會算錯而且沒人知道為什麼。

### 分頁三「分配」——回答問題 3,只有管理員看得到

一張矩陣:列是人,欄是專案。這是整個功能裡唯一需要被「規劃」的畫面。

```
┌─ 時段 ─┬─ 假期 ─┬─ 分配 ─┐

成員        Alpha   Beta   Gamma    合計    行事曆    每日工時
Ana          50%    50%      —      100%    台灣      8h
Bob          30%    30%     40%     100%    德國      8h
Cara         60%    60%      —      120% ⚠  台灣      8h
Dan           —      —       —        0%    台灣      6h

⚠ Cara 被分配了 120%。兩個專案的計畫加起來超過她實際有的時間。
```

- 合計超過 100% 直接是 `clean()` 的驗證錯誤,不是警示標籤。**擋在寫入點,不是提醒。**
- 「0%」不是錯誤,是「還沒被分到任何專案」——顯示出來,因為未分配的產能是規劃時要找的東西。
- 每日工時與行事曆在同一張表上編輯,因為它們是同一個決定的三個面向。

### 第四個畫面:Cycle 產能面板(在專案裡,不在這頁)

```
Sprint 24 · 8/10–8/23 · 工作日 10 天(含 8/15 補班)

成員     分配   毛工時   請假    事件   本專案可用
Ana      50%     80h    −12h     −4h      32h
Bob      30%     80h      —      −4h      22.8h
Cara     60%     80h    −40h     −4h      21.6h
                                   合計    76.4h

已承諾 92h · ⚠ 超出 15.6h
```

- 「已承諾」這一行**只在專案的估點制度是 `TIME` 時出現**。用故事點的專案看到的是可用人日與一句
  說明,而不是把點數和小時湊成一個看起來可比的比率。
- 請假與事件同一天不會重複扣——服務層用每日占用率表且上限 1.0(見 ADR 0008)。

## 分配怎麼算(回答「怎麼分配比較好」)

規則只有三條:

1. **缺席按比例影響所有專案。** Ana 五五分在 Alpha 和 Beta,請一天假 → 兩邊各少 4 小時,不是
   某一邊少 8 小時。人不是跟專案請假的。
2. **可用工時 = 工作日 × 每日工時 × 分配比例 − 缺席佔用。** 工作日來自這個人綁定的行事曆,所以
   台北的人和柏林的人在同一個 sprint 裡的工作日天數本來就可能不同。
3. **分配總和不得超過 100%。** 這是唯一的硬性約束,也是這張表存在的理由。

不做的事:分配不做生效日期。改分配會改變已結束 cycle 的計算結果。這是已知限制,寫在 ADR 0008
裡——升級路徑很明顯(加 `effective_from`/`effective_to` 與區間重疊驗證),但這一輪的產能數字是
規劃輸入,為了回顧準確度付這個複雜度不划算。

## 讀寫路徑

| 畫面         | 讀                                                  | 寫                                                 |
| ------------ | --------------------------------------------------- | -------------------------------------------------- |
| 時段(週視圖) | `GET .../availability/schedule/?from&to`            | 無(衍生)                                           |
| 找共同時段   | `POST .../availability/overlap/`                    | 無                                                 |
| 假期(月曆)   | `GET .../availability/leaves/?from&to` + `/events/` | `POST /leaves/`、`PATCH /leaves/<id>/`(核准、取消) |
| 分配矩陣     | `GET .../availability/allocations/`                 | `PUT .../allocations/<member>/`                    |
| 我的工作設定 | `GET .../availability/profiles/<member>/`           | `PATCH` 同路徑                                     |
| Cycle 產能   | `GET .../projects/<id>/cycles/<id>/capacity/`       | 無(衍生)                                           |

所有寫入都走 `plane/availability/services.py`,`@transaction.atomic`。View 是薄轉接。

## 人與 agent 同能力(守則 A3 三處同步)

每個 UI 動作都有等價的 MCP tool 與 CLI 指令:

| UI 動作    | MCP                     | CLI                              |
| ---------- | ----------------------- | -------------------------------- |
| 登記請假   | `leave_request`         | `plane-qa leave request`         |
| 看誰不在   | `leave_list`            | `plane-qa leave list`            |
| 核准/駁回  | `leave_approve`         | `plane-qa leave approve`         |
| 找共同時段 | `availability_overlap`  | `plane-qa availability overlap`  |
| 看週時段   | `availability_schedule` | `plane-qa availability schedule` |
| 改分配     | `allocation_set`        | `plane-qa allocation set`        |
| Cycle 產能 | `cycle_capacity`        | `plane-qa capacity cycle`        |

「幫我找下週三個人都有空的兩小時」應該是一句話就能做到的事——這是這個功能最自然的 agent 用法,
也是三處同步在這裡不是形式主義的原因。
