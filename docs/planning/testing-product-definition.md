# Testing 產品定義 —— Persona、Jobs-to-be-Done、介面設計與需求分類

> 狀態:草稿 v0.9 · 2026-07-28 · #4 #6 #11 #14 #18 已完成;新增 #14–#19
> 範圍:自用、多團隊多專案 · 執行形式:混合(關鍵路徑自動化)
> 這份文件是**共同基礎、已排序的 backlog 與介面設計判準**,不是實作規格。每個缺口各自走一輪 spec → plan → 實作。

## 論點

這套系統的價值全部押在一條鏈上:一個需求如何變成可執行的驗收契約、如何被驗證、失敗如何變成可重現的任務、修好後如何回到證據裡。

鏈是完整的 —— **資料層完整,呈現層斷裂**。以下每個斷點都已在程式碼中定位。

## 證據鏈與它的斷裂處

```
需求 ──✕── 驗收契約 ──── 一輪驗證 ──── 證據 ──✕── 缺陷 ──✕── 重現與修復 ──✕── 重驗
Work item      Test case      Test run      Result    Defect issue    RD / RD agent   Retest result
```

`✕` 表示資料層存在關聯,但使用者在介面上走不過去。

四道斷裂與其成因:

| 斷裂        | 成因                                                                          |
| ----------- | ----------------------------------------------------------------------------- |
| 需求 ↔ 契約 | 連結要手貼 UUID(建立後已可點、可解除 —— #4 已修)                              |
| 證據 → 缺陷 | `create_defect_from_result` 只撈 `actual_result.get("text")`,附件與截圖被剝除 |
| 缺陷 → 重現 | 缺陷描述回不到來源 run / case                                                 |
| 重現 → 重驗 | 要自己翻回原本那一輪                                                          |

共同成因曾是:Testing 分頁沒有 URL 路由,任何深連結都做不出來。**該阻擋項已於 #11 解除** —— 每個實體現在都可定址(見附錄 C 之後的路由結構)。四道斷裂仍在,但已從「技術上做不到」變成「尚未接上」。

## 第 1 節 · Persona

四個人類 persona 加兩個系統 actor。刻意壓到最少 —— 角色會依團隊成熟度崩塌(有專職 QA 的團隊與沒有的團隊共用這份文件),所以「同一個人做多件事」交給 JTBD 主幹處理,persona 本身要穩定。

### P1 · 測試設計者

- **誰扮演**:有專職 QA 的團隊 = QA analyst;沒有的團隊 = PM 或資深 dev
- **核心目標**:讓每個需求都有明確、可執行、不會過期的驗收契約
- **成功長什麼樣**:coverage 沒有未覆蓋的需求;別人照著 case 就能跑
- **現在最痛**:連結需求要手貼 UUID;看不到哪些情境已被自動化覆蓋,因此重複設計

### P2 · 執行者

- **誰扮演**:QA;小團隊可能是 dev 互測
- **核心目標**:在一次 build 裡跑完該跑的,並留下可信的證據
- **成功長什麼樣**:一輪跑完不用切視窗;失敗能一鍵變成有證據的缺陷
- **現在最痛**:執行體驗其實已經不錯(`execution-workspace.tsx` 已有 P/F/B/S 鍵盤流)。真正的痛是**證據記不下來** —— 貼不了圖、傳不了檔;以及重驗時要自己翻回原本那一輪

### P3 · 開發者

- **誰扮演**:RD。身兼「自動化作者」與「缺陷修復者」兩個 job,由主幹區分
- **核心工作流**:接任務 → **照 QA 的步驟重現同樣現象** → 修復 → 回報狀態
- **成敗關鍵**:是「重現」不是「修」。重現需要完整步驟、前置條件、**截圖或錄影**、實際觀察
- **現在最痛**:
  1. 缺陷描述只有純文字,截圖與附件在建立當下就被剝除
  2. 缺陷回不去來源 run / case(反向已通:契約詳情看得到歷次驗證 —— #6 已修)
  3. (另一頂帽子)CI 自動建立的 case 會孤兒化,介面沒有任何待歸檔提示

### P4 · 交付決策者

- **誰扮演**:PM / PO
- **核心目標**:回答「這個需求驗過了嗎」與「這一版能不能出」
- **成功長什麼樣**:不進 Testing 分頁也能知道狀態;出貨決策有依據,不是憑印象
- **現在最痛**:需求頁上的覆蓋率面板是死的(`issue-detail/testing-summary.tsx`)—— 看得到 TC-3 失敗,點不進去

### S1 · CI Pipeline(系統 actor)

- **能力**:冪等寫入 —— 同 key 重放回 200,payload 變了回 409 而非靜默覆蓋
- **設計時不能忘**:它會**自動產生 test case**。未映射的結果會建立標記 `automated` 的 case
- **現況**:上傳可挾帶 artifact —— **人工執行反而不行**,這是個不對稱

### S2 · 開發者的 Agent(系統 actor)

- **能力**:透過 MCP / CLI 抓取任務細節 → 依證據重現 → 修復 → 回寫狀態
- **為何列為一級**:這是本系統相對 Jira / TestRail 的**差異化能力**。只考慮人類介面等於放棄它
- **設計約束**:**人在介面上能做的,agent 都要能做到同樣完整;agent 寫入的內容,人也要能在介面上看懂並追溯**
- **現在最痛**:agent 拿到的證據跟人一樣殘缺 —— 描述被剝成純文字後,再聰明的 agent 也重現不了

## 附錄 C · 四個實體的生命週期

這四個實體的不變量是系統的核心保證 —— 它們已經在模型層被強制,設計時只能順著走,不能繞過。

### 驗收契約(Test case)

```
建立 → 編輯:發布新的不可變版本 → 連結需求 → 被 run 釘住版本 → [封存]
```

- **不變量**:編輯永遠發布新版本,舊版本永遠可讀。歷史不被改寫
- **誰碰得到**:P1 建立維護 · P3 自動化 case · P2 執行時讀
- **缺什麼**:建立連結仍要手貼 UUID(#1);版本歷史無法瀏覽。執行歷史與可點可解除的需求連結已補上(#6 #4)

### 一輪驗證(Test run)

```
建立:釘住當下的 case 版本 → 執行中 → [關閉:拒絕新結果]
```

- **不變量**:建立時釘住版本,契約之後的編輯不影響已存在的 run。關閉後拒絕一切結果
- **誰碰得到**:P2 建立與執行 · S1 自動建立 · P4 讀進度
- **缺什麼**:綁不到 sprint(#10);挑 case 的體驗破碎(#9 #12)

### 證據(Test result)

```
追加 → [永不修改、永不刪除]
```

- **不變量**:只能追加。更正錯誤的方式是**追加一筆新結果並在內容說明**,不是改舊的
- **誰碰得到**:P2 記錄 · S1 上傳 · P3 與 S2 讀取以重現
- **缺什麼**:無法附上任何證據(#2)—— 這是整條鏈上游的源頭

### 缺陷(Defect = 真正的 Plane work item)

```
從 failed / blocked 原子建立 → 進入 backlog → 修復 → [狀態群組進 completed / cancelled 才算關閉]
```

- **不變量**:只能從失敗或受阻的結果建立,且與結果連結是同一筆交易。它是真的 work item,走一般 issue 流程
- **誰碰得到**:P2 建立 · P3 與 S2 修復 · P4 排程與出貨判定
- **缺什麼**:證據在建立當下被剝除(#3);回不去來源 run / case —— 路由已備妥(#11),缺的是把連結接上

## 可追溯性設計原則

這些原則用來裁決後續每一個介面決定。它們不是功能清單,是**判準**:任何新設計違反其中一條,就退回重想。

### 每一個關聯都要雙向可走

現況的關聯幾乎都是單向可見:A 看得到 B 存在,卻點不過去;或 B 根本不知道 A 的存在。凡是資料層有連結的地方,**兩端都要有可點的入口**。

- **契約 ↔ 需求**:契約要列出需求的名稱與狀態且可點;需求頁的覆蓋率面板每列可點回契約
- **證據 → 缺陷**:已有。**缺陷 → 證據 / 一輪驗證 / 契約**:缺
- **契約 → 歷次驗證**:缺。這是 P1 與 P3 都要的視角

### 證據必須完整跨越交接點

QA 記下的東西,RD 或其 agent 要**原封不動**拿到。任何在交接時剝除資訊的轉換都是缺陷,不是取捨。這條原則直接來自 J4 的失敗模式。

- 實際結果的富文本與附件,要完整帶進缺陷描述
- 附件實體要能同時被結果與缺陷 work item 參照,不是複製兩份

### 人與 agent 同能力

凡人在介面上能做的,MCP 與 CLI 都要能做到同樣完整;凡 agent 寫入的內容,人在介面上都要看得懂並能追溯。這是 S2 存在的前提,也是這套系統相對商業工具的差異點。

- 新增任何介面動作時,同步確認對應的 MCP tool 與 CLI 指令存在且參數等價
- agent 的寫入要留下可辨識的來源,人才能判斷這筆是誰做的

### 深連結是基礎設施,不是功能

每個實體都要有可定址的網址。這是前面三條原則的**技術前提** —— 沒有它,「可點過去」在實作上無從談起。

**此原則已落實(#11)**,以下路由結構已上線;新增任何實體時比照辦理。

已上線的路由結構:

```
/testing                         → 導向 overview
/testing/overview
/testing/cases                   → 可帶 ?folder= 篩選
/testing/cases/:sequence         → 單一契約,需求頁由此連入
/testing/runs
/testing/runs/:runId             → 一輪驗證
/testing/runs/:runId/:runCaseId  → 單一執行項,缺陷由此連回
```

### 不可變性要在介面上被看見

版本化、追加式結果、釘住版本 —— 這些是系統最有價值的保證,但使用者現在幾乎感覺不到。部分已呈現(編輯時會提示將產生新版本、執行時顯示釘住的版本號),但**看不到歷史本身**。

- 契約要能瀏覽版本歷史,並看出哪一版被哪些驗證釘住
- 結果以時間軸呈現每次追加,讓「失敗 → 修復 → 重驗」的歷程可讀

## 第 5 節 · 企業敏捷層級與需求分類

本節回答一個先前沒處理的問題:這套系統要不要、以及能不能承載企業敏捷的需求結構。結論是**骨架可以,但有三處實質落差**,構成 #14 #15 #16 —— 三者皆已修復。相關的 #17 只完成一半,見 backlog 表。

### 兩個不同維度,不是同一條鏈

常見的誤解是把它們串成一條:`Epic → Feature → Story → FR → NFR → Task`。這是錯的。

- **Epic / Feature / Story / Task** 是**工作拆解結構**,回答「工作要怎麼拆、怎麼排進開發」
- **FR / NFR** 是**需求性質分類**,回答「系統要做什麼、要做到什麼程度」

兩者是交叉關係:FR 與 NFR 橫跨每一個工作層級。

**白話速記:** Epic ≈ 商業能力(口語可近似 journey);Feature = 連貫系統能力;Story = 迭代交付價值(契約掛點)——**不是**「requirement 再拆 FR / NFR」。FR / NFR 是 `requirement_kind` 橫切標籤。完整對照表見 `docs/process/plane-qa-guideline.md` B2「白話速記」。

```
Business Goal
└── Epic
    └── Feature
        ├── Story
        │   ├── FR / Acceptance Criteria
        │   ├── BDD Scenario
        │   └── Task
        └── Feature-level NFR
System
└── System-level NFR
```

### 價值鏈:Story 到 Test Case

```
Story              這次要交付什麼使用者價值
  ↓
FR / NFR / Rules   系統要做到什麼、做到什麼程度
  ↓
Acceptance Criteria  滿足哪些條件才算完成
  ↓
BDD Scenario       用 Given / When / Then 驗證這些條件
  ↓
Test Case          用具體資料與操作實際執行
  ↓
結果回流            執行 → 缺陷 → 修復 → 重驗
```

**最後那道回流才是價值閉環與數據飛輪的基底** —— 也是本系統目前最完整的部分。

### 系統的對應能力

| 層級                    | 系統對應                                              | 狀態                              |
| ----------------------- | ----------------------------------------------------- | --------------------------------- |
| Business Goal           | Initiative(workspace 層)                              | ✅                                |
| Epic                    | Work item type(`IssueType.is_epic` / `level`)         | ✅                                |
| Feature                 | Work item type,`Issue.parent` 指向 Epic               | ✅ 資料層可任意深度               |
| Story                   | Work item type,`parent` 指向 Feature                  | ✅                                |
| FR / NFR 分類           | `Issue.requirement_kind`(functional / quality / none) | ✅ 見下方說明                     |
| Acceptance Criteria     | **Test case 本身**                                    | ✅ 系統設計即如此                 |
| BDD Given / When / Then | `preconditions` + `steps[{action, expected_result}]`  | ✅ 對應乾淨                       |
| Test Case 具體資料      | 自由文字 JSON                                         | ⚠️ 無 Scenario Outline / Examples |
| 結果回流                | run → result(append-only)→ defect → 重驗              | ✅ **最完整**                     |

**FR / NFR 分類落在 `Issue.requirement_kind`,既不是 type 也不是 property。** 這一條前後換過三次落點,值得完整記下來,因為前兩次都是被「跟現況一致」推著走的:

| 時期    | 落點                                                  | 為什麼被換掉                                                                                                                  |
| ------- | ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 最初    | work item property(select)                            | property 是**專案層級**定義:每開一個新專案都要先建它問題才問得出來,跨專案報表則根本問不出來                                   |
| 2026-07 | work item type(「Quality requirement」,與 Story 同階) | type 已經用 `level` 承載「多寬」,再讓它承載「什麼性質」會讓 type 數量變成 `層數 × 性質數` —— 一個 workspace 因此長到九個 type |
| 現行    | `Issue.requirement_kind` 欄位                         | —                                                                                                                             |

第二次改動的理由當時寫的是「跟 DEMO 一致」。文件與程式確實一致了,但一致的對象是一個會讓 type 數量相乘的設計 —— **一致不等於正確**。第 5 節警告的「把性質軸折進拆解軸」講的就是這個塌陷,而它正是靠這次改動被引進來的。

改成欄位之後兩個軸才真的分開:拆解層級由 `IssueType.level` 承載,需求性質由 `requirement_kind` 承載,任何層級都能自由組合。property 仍然可用,適合在性質之下再細分(例如安全 / 效能 / 可用性),但不該拿來承載主要分類。

`none` 的語意是**「不是需求」**,不是「還沒分類」(那是 null,而這個欄位不允許 null):Task 是需求的實作、Bug 是缺陷,兩者都帶 `none`;Epic 與 Feature 是需求,只是比 Story 寬。完整論證見 `docs/process/plane-qa-guideline.md` B2。

**刻意的結構壓縮**:本模型把 FR / AC / BDD / Test Case 四層壓縮成 **test case 一個物件**。這與 role-playbooks 的立場一致(「Acceptance contract = Test case linked to the requirement」)。若追蹤重心放在 Feature → Story 的價值交付,這個壓縮是划算的;若需要 `FR-XXX-001` 這種可獨立追蹤的識別碼,FR 就得各自成為 work item,數量會顯著膨脹。**這是取捨,不是缺陷。**

### NFR 驗收的四種形態

NFR **不是「跑一次測試就驗完」**。實務上有四種節奏與證據來源都不同的形態。

**這是驗證軸,不是內容分類。** 企業常見的 NFR 清單(Performance、Availability、Security、Scalability、Compliance 等)分的是**約束哪一種品質屬性**;以下四形態分的是**證據從哪來、多久產一次**。兩軸正交——同一個內容類別會依驗收條件怎麼寫落在不同形態(Reliability 的冪等性是形態 1,故障恢復是形態 4),因此不可用單一欄位表達。內容類別到形態的對照表在 `docs/process/plane-qa-guideline.md` B3。

| 形態           | 例子                                | 驗證方式                                    | 節奏                            | 系統支援                       |
| -------------- | ----------------------------------- | ------------------------------------------- | ------------------------------- | ------------------------------ |
| **1 門檻量測** | P95 < 2s、50 TPS、千萬筆資料下可查  | k6 / JMeter / Locust 產生**量測值**比對門檻 | release candidate,非每次 commit | ✅ 今天即可                    |
| **2 掃描**     | 密碼不得明文、TLS 1.2+、無已知 CVE  | SAST / DAST / 依賴稽核                      | 每次 PR / nightly               | ⚠️ 可轉 JUnit 上傳,通常留在 CI |
| **3 審查**     | 可維護性、可觀測性、稽核保留 365 天 | checklist / ADR / 架構審查                  | 一次性或架構變更時              | ❌ 無 checklist 物件           |
| **4 持續 SLO** | 可用性 99.9%、RPO 15min / RTO 2h    | 生產環境持續量測 + DR 演練                  | 持續 + 定期演練                 | ❌ 無                          |

**第 4 類在出貨前根本無法「測試」** —— 可用性是上個月的量測結果,RTO 要靠演練證明。這類 NFR 永遠不該變成 test case;硬做會得到一個每天「執行」卻不代表任何一次測試的假 case。

形態 1 今天就能完整落地:k6 輸出 JUnit XML → `automation_upload_junit` 帶穩定 `external_id` → 每次執行掛回同一個 NFR case,其歷次結果即效能趨勢。

```
Test case: NFR-PERF-001 訂單歷程查詢 P95 < 2s
  Given   資料庫有 1,000 萬筆歷程
  When    以有效訂單編號執行查詢(200 VU,持續 5 分鐘)
  Then    P95 回應時間 < 2000ms
```

**因此 NFR 的真正瓶頸不是「不能寫 NFR test case」,而是 release gate 需要外部證據接口** —— 這是 #15,已完成:`ReleaseEvidence`(`kind` = slo / scan / review / other)承接測試產不出來的證據,出貨閘門把 `failing` 與 `pending` 都列為 blocker。

### 術語:為何只動呈現層

SDK / CLI / MCP 的工具名稱與輸入結構是**公開契約**(見 codebase-map:removals/renames 需 major version + migration note)。把 `test_run_create` 改成 `test_execution_create` 會打斷所有 agent、CI 腳本與 CLI 使用。

**術語改造一律只動呈現層。** 而 testing UI 目前完全沒接 i18n(其他功能都有 `packages/i18n/src/locales/*/`,testing 僅在 `navigation.json` 有一個 key),因此改術語的正確做法是**先接 i18n**,見 #16。

`Cycle`(Sprint)與 `Module`(Epic / Feature)屬 Plane 上游核心概念,全面改名會波及整個 app 並製造大量上游 rebase 衝突 —— 建議僅以 i18n 覆寫顯示名稱,改資料檔而非程式碼。

### FR 與 NFR 的介面配置:三分,不是二分

FR 與 NFR 的差異夠大,但**不足以構成兩個並列頁面**。最大的差異在「結果的形狀」:

|          | FR                | NFR                                         |
| -------- | ----------------- | ------------------------------------------- |
| 歸屬層級 | 綁單一 Story      | 可能綁 Story / Feature / System **三層**    |
| 結果形狀 | pass / fail(布林) | **量測值**(P95 = 1,840 ms)—— 有數值、有趨勢 |
| 驗收節奏 | 隨 Story 完成     | 四形態各異(per-PR / per-RC / 持續)          |
| 執行環境 | 一般測試環境      | prod-like 資料量 + 負載工具                 |
| 生命週期 | Story 關閉即結束  | **長期存在,持續回歸**                       |

**業界已收斂**:TestRail、qTest、PractiTest 皆採「單一 case repository + `type` 欄位 + 儲存檢視」;Jira + Xray 則把效能測試放在體系外只回傳摘要。**沒有主流工具把 FR 與 NFR 做成兩個對等頁面**,因為那會把一個需求的驗收證據拆到兩處。

分成兩頁在本系統會直接違反自訂判準:違反「每一個關聯都要雙向可走」(同時有 FR 與 NFR 的 Story 要看兩處)、coverage 需跨兩邊合併(#14 已在處理階層維度,再加一維更難)、release gate 需讀兩個來源。

但直接混進同一張表同樣不可行:FR 不需要「門檻」欄位,NFR 不需要資料夾分類卻很需要「最新量測值」。

**因此依四形態切成三份:**

| 內容                             | 放哪                                               | 理由                             |
| -------------------------------- | -------------------------------------------------- | -------------------------------- |
| 功能驗收(FR)                     | Test case,`type = functional`                      | 現況                             |
| **可量測的 NFR**(形態 1、2)      | **同一個 case 庫**,`type = performance / security` | 會被執行、會產生結果、需要回歸   |
| **持續 / 審查型 NFR**(形態 3、4) | **不進 case 庫** → Release Gate 外部證據           | 出貨前無法測試,硬做會產生假 case |

#### 介面配置

**Case detail 依 `type` 換渲染。** 功能型維持 Given / When / Then 加 pass-fail 時間軸;門檻型改為:

```
Given     1,000 萬筆歷程 · 200 VU · 持續 5 分鐘
When      以訂單編號查詢
Then      P95  <  2,000 ms          ← 結構化欄位,非自由文字
─────────────────────────────────
最新量測   1,840 ms   達標   餘裕 8%
趨勢      最近 10 次折線
來源      k6 · CI run #482
```

門檻必須結構化為 `{metric, operator, threshold, unit}`,量測值為 `{measured, unit}`。塞在自由文字裡就畫不出趨勢、也無法自動判定。**`expected_result` 與 `actual_result` 皆已是 JSONField,不需 migration** —— 與 rich text 的情況相同,缺的只是渲染與寫入端。

**Case 清單不分頁,加 `type` 欄位與檢視切換**(全部 / 功能 / 效能 / 安全),清單欄位隨檢視變換:功能看 priority,門檻看最新量測。

**Overview 新增「出貨門檻」區塊**,把 #15 從抽象接口變成可見的東西:

```
出貨門檻
  功能測試       42/42 通過
  效能門檻        3/3 達標
  未結缺陷        1 件 · DEMO-5
  安全掃描        0 高風險            ← 外部證據
  SLO 上月達標     99.7% < 99.9%      ← 外部證據
  架構審查簽核     待簽                ← 外部證據
```

前三行來自 test management,後三行來自外部來源。

#### 一個容易混淆的區分

**work item 上的 FR / NFR 分類 ≠ test case 上的 `type`。**

- work item 的分類 → 這條**需求本身**是功能還是品質要求(需求管理)
- test case 的 `type` → 這個**驗收契約用什麼方式驗**(測試管理)

兩者不同:一條功能需求的驗收條件完全可能包含一個效能門檻。**不要用同一個欄位表達兩件事。**

## 附錄 D · DEMO 範例專案

`DEMO / Order Service Platform` 依第 5 節的結構建立,取材自通用軟體交付場景(訂單 / 物流單號歷程、退貨誤判更正、區域權限)——刻意不綁任何特定產業,好讓讀者不必先懂某個 domain 才讀得懂模型。它的用途不只是有資料可看,而是**讓三個軸各自獨立可見**。

### 三個軸交叉,而非巢套

| 軸           | 承載方式                           | 值                                        |
| ------------ | ---------------------------------- | ----------------------------------------- |
| **工作拆解** | `IssueType.level` + `Issue.parent` | Epic → Feature → Story                    |
| **需求性質** | `Issue.requirement_kind`           | functional / quality / none               |
| **時間箱**   | Cycle                              | Sprint 2026-07B(已交付)/ 2026-08A(進行中) |

三者互不決定彼此,seed 後的實際資料可見(節錄,`#` 為 `sequence_id`):

```
#    LEVEL    KIND        SPRINT            STATE
2    Epic     quality     —                 started     ← Epic 也可以整條是品質要求
4    Epic     functional  —                 cancelled   ← 性質與狀態無關,取消的仍是需求
8    Feature  quality     —                 started     ← Feature 層的品質約束
12   Story    quality     Sprint 2026-07B   completed
18   Story    functional  Sprint 2026-08A   unstarted   ← 零契約,擋住門檻
22   Story    quality     —                 backlog     ← 有性質、有層級,但不屬於任何 sprint
27   Bug      none        —                 completed   ← 缺陷不是需求,性質軸為 none
```

**性質橫跨每一個層級,這正是它必須是欄位而不是 type 的理由。** 若把性質折進 type,`通知服務可靠性`(#2,整條 epic 都是品質要求)與 `通知送達即時性`(#8,feature 層的品質約束)就各自需要一個新 type,type 數量會變成 `層數 × 性質數`。先前版本確實走過這條路——把「品質需求」做成與 Story 同層的 work item type,正是第 5 節警告的那種塌陷。

`none` 的意思是**「不是需求」**,不是「還沒填」。#27 那一列不是資料缺漏:缺陷是需求**失效的證據**,不是需求本身,所以覆蓋率報表必須自己排除它。同理 Task 是需求的實作,也帶 `none`。

### Epic 層:五個,而不是同一列的五種寫法

上面那段實測輸出取自只有兩個 epic 的版本,而那兩個在 `/epics` 頁面會分組的每一個欄位上都相同——同一個 state、同一個 priority、都沒有日期。頁面本身是依 `type__is_epic` 過濾的 work item 清單,所以「能分組、能排位、能畫進度」全都要靠 epic 之間的**差異**才顯現得出來,一列重複五次證明不了任何事。

| Epic                   | state group | priority | 窗期      | 它示範什麼                             |
| ---------------------- | ----------- | -------- | --------- | -------------------------------------- |
| 訂單歷程與退貨追溯能力 | started     | urgent   | -55 → +25 | 後代鋪滿五種 state group,含一筆逾期    |
| 通知服務可靠性         | started     | high     | -30 → +45 | 第二個進行中的 epic,分組不再是單元素   |
| 對帳報表與法規保存     | unstarted   | medium   | +14 → +75 | 窗期完全在未來,尚未動工                |
| 客服工作台前端改版     | cancelled   | low      | -90 → -20 | 取消的工作**留在分母**,放棄 ≠ 接近完成 |
| 消費者自助退貨申請     | backlog     | none     | —         | 沒有後代,進度區塊整段不渲染            |

窗期是相對今天的天數偏移,不是寫死的日期——seed 下個月再跑一次必須一樣合理。Epic 不屬於任何 sprint(它跨 sprint),所以這對日期是它唯一能有窗期的來源,而 gantt 與 calendar 兩種 layout 完全靠它排位。

逾期的判定只落在**仍然開著**的後代上:已完成或已取消而過了目標日的項目是做完了或砍掉了,不是遲交,標紅會讓一個準時交付的 epic 看起來延誤。

### 系統層 NFR 不是 test case

依第 5 節的四形態,DEMO 把 NFR 分成兩種落點:

- **可執行的**(P95 門檻、失敗率門檻、區域權限)→ test case,有 `case_type` 與結構化門檻
- **系統層的**(可用性、DR 演練、相依稽核、TLS 基線、架構簽核)→ **release evidence**,不是 case

門檻案例各有兩次量測(前後兩個 sprint),所以趨勢存在而非單點讀數。

### 敏捷節奏

兩個 sprint 各有一輪驗證,綁定各自的 cycle 與 build。其中一個 Story(歷程匯出)自 07B 順延到 08A,示範跨 sprint 的結轉。TC-1 在 07B 執行後被編輯發布 v2,而**已關閉的 sprint 仍釘住它當初執行的 v1** —— 不可變性在畫面上看得見。

### 它證實了什麼

| 觀察                                                                | 對應             |
| ------------------------------------------------------------------- | ---------------- |
| Epic #1 繼承 10 個契約、Feature #3 繼承 6 個                        | #14 階層 roll-up |
| 兩個缺陷完全不在覆蓋率清單裡                                        | #14 型別過濾     |
| `requirements.coverage_percent` 93.3%,`library.linked_percent` 100% | #14 指標分離     |
| 門檻同時被「1 個需求無契約」與「可用性未達標」擋下                  | #18 + #15        |
| TC-1 在 08A 釘 v2、在 07B 仍釘 v1                                   | 版本不可變       |

### 重建方式

```bash
python manage.py seed_testing_demo --workspace <slug> [--identifier DEMO] [--owner <email>] [--force]
```

同識別碼的專案已存在時會拒絕執行,必須明確加上 `--force` 才會取代 —— 它會連同該專案的所有 work item、測試契約、執行與結果一併刪除。整個 seeding 在單一 transaction 內完成。

所有測試資產皆透過 `plane.testing.services` 建立,因此版本不可變、run 釘版本、結果僅追加、缺陷僅能從 failed/blocked 產生這些不變量都會被實際強制,不會產生繞過服務層的髒資料。
