# Testing 產品定義 —— Persona、Jobs-to-be-Done 與介面設計

> 狀態:草稿 v0.2 · 2026-07-28
> 範圍:自用、多團隊多專案 · 執行形式:混合(關鍵路徑自動化)
> 這份文件是**共同基礎、已排序的 backlog 與介面設計判準**,不是實作規格。每個缺口各自走一輪 spec → plan → 實作。

## 論點

這套系統的價值全部押在一條鏈上:一個需求如何變成可執行的驗收契約、如何被驗證、失敗如何變成可重現的任務、修好後如何回到證據裡。

鏈是完整的 —— **資料層完整,呈現層斷裂**。以下每個斷點都已在程式碼中定位。

## 證據鏈與它的斷裂處

```
需求 ──✕── 驗收契約 ──── 一輪驗證 ──── 證據 ──✕── 缺陷 ──✕── 重現與修復 ──✕── 重驗
Work item      Test case      Test run      Result    Defect issue    RD / RD agent   Retest result
```

`✕` 表示資料層存在關聯,但使用者在介面上走不過去。

四道斷裂與其成因:

| 斷裂        | 成因                                                                          |
| ----------- | ----------------------------------------------------------------------------- |
| 需求 ↔ 契約 | 連結要手貼 UUID;建立後只顯示數量、不可點、無法解除                            |
| 證據 → 缺陷 | `create_defect_from_result` 只撈 `actual_result.get("text")`,附件與截圖被剝除 |
| 缺陷 → 重現 | 缺陷描述回不到來源 run / case                                                 |
| 重現 → 重驗 | 要自己翻回原本那一輪                                                          |

共同成因:Testing 分頁沒有 URL 路由(`apps/web/.../testing/page.tsx` 以區域 state 管理分頁),**任何深連結在今天都做不出來**。

## 第 1 節 · Persona

四個人類 persona 加兩個系統 actor。刻意壓到最少 —— 角色會依團隊成熟度崩塌(有專職 QA 的團隊與沒有的團隊共用這份文件),所以「同一個人做多件事」交給 JTBD 主幹處理,persona 本身要穩定。

### P1 · 測試設計者

- **誰扮演**:有專職 QA 的團隊 = QA analyst;沒有的團隊 = PM 或資深 dev
- **核心目標**:讓每個需求都有明確、可執行、不會過期的驗收契約
- **成功長什麼樣**:coverage 沒有未覆蓋的需求;別人照著 case 就能跑
- **現在最痛**:連結需求要手貼 UUID;看不到哪些情境已被自動化覆蓋,因此重複設計

### P2 · 執行者

- **誰扮演**:QA;小團隊可能是 dev 互測
- **核心目標**:在一次 build 裡跑完該跑的,並留下可信的證據
- **成功長什麼樣**:一輪跑完不用切視窗;失敗能一鍵變成有證據的缺陷
- **現在最痛**:執行體驗其實已經不錯(`execution-workspace.tsx` 已有 P/F/B/S 鍵盤流)。真正的痛是**證據記不下來** —— 貼不了圖、傳不了檔;以及重驗時要自己翻回原本那一輪

### P3 · 開發者

- **誰扮演**:RD。身兼「自動化作者」與「缺陷修復者」兩個 job,由主幹區分
- **核心工作流**:接任務 → **照 QA 的步驟重現同樣現象** → 修復 → 回報狀態
- **成敗關鍵**:是「重現」不是「修」。重現需要完整步驟、前置條件、**截圖或錄影**、實際觀察
- **現在最痛**:
  1. 缺陷描述只有純文字,截圖與附件在建立當下就被剝除
  2. 缺陷回不去來源 run / case,看不到該 case 的其他執行歷史
  3. (另一頂帽子)CI 自動建立的 case 會孤兒化,介面沒有任何待歸檔提示

### P4 · 交付決策者

- **誰扮演**:PM / PO
- **核心目標**:回答「這個需求驗過了嗎」與「這一版能不能出」
- **成功長什麼樣**:不進 Testing 分頁也能知道狀態;出貨決策有依據,不是憑印象
- **現在最痛**:需求頁上的覆蓋率面板是死的(`issue-detail/testing-summary.tsx`)—— 看得到 TC-3 失敗,點不進去

### S1 · CI Pipeline(系統 actor)

- **能力**:冪等寫入 —— 同 key 重放回 200,payload 變了回 409 而非靜默覆蓋
- **設計時不能忘**:它會**自動產生 test case**。未映射的結果會建立標記 `automated` 的 case
- **現況**:上傳可挾帶 artifact —— **人工執行反而不行**,這是個不對稱

### S2 · 開發者的 Agent(系統 actor)

- **能力**:透過 MCP / CLI 抓取任務細節 → 依證據重現 → 修復 → 回寫狀態
- **為何列為一級**:這是本系統相對 Jira / TestRail 的**差異化能力**。只考慮人類介面等於放棄它
- **設計約束**:**人在介面上能做的,agent 都要能做到同樣完整;agent 寫入的內容,人也要能在介面上看懂並追溯**
- **現在最痛**:agent 拿到的證據跟人一樣殘缺 —— 描述被剝成純文字後,再聰明的 agent 也重現不了

## 附錄 C · 四個實體的生命週期

這四個實體的不變量是系統的核心保證 —— 它們已經在模型層被強制,設計時只能順著走,不能繞過。

### 驗收契約(Test case)

```
建立 → 編輯:發布新的不可變版本 → 連結需求 → 被 run 釘住版本 → [封存]
```

- **不變量**:編輯永遠發布新版本,舊版本永遠可讀。歷史不被改寫
- **誰碰得到**:P1 建立維護 · P3 自動化 case · P2 執行時讀
- **缺什麼**:執行歷史沒有回顯(#6);需求連結是啞的(#1 #4);版本歷史無法瀏覽

### 一輪驗證(Test run)

```
建立:釘住當下的 case 版本 → 執行中 → [關閉:拒絕新結果]
```

- **不變量**:建立時釘住版本,契約之後的編輯不影響已存在的 run。關閉後拒絕一切結果
- **誰碰得到**:P2 建立與執行 · S1 自動建立 · P4 讀進度
- **缺什麼**:綁不到 sprint(#10);挑 case 的體驗破碎(#9 #12)

### 證據(Test result)

```
追加 → [永不修改、永不刪除]
```

- **不變量**:只能追加。更正錯誤的方式是**追加一筆新結果並在內容說明**,不是改舊的
- **誰碰得到**:P2 記錄 · S1 上傳 · P3 與 S2 讀取以重現
- **缺什麼**:無法附上任何證據(#2)—— 這是整條鏈上游的源頭

### 缺陷(Defect = 真正的 Plane work item)

```
從 failed / blocked 原子建立 → 進入 backlog → 修復 → [狀態群組進 completed / cancelled 才算關閉]
```

- **不變量**:只能從失敗或受阻的結果建立,且與結果連結是同一筆交易。它是真的 work item,走一般 issue 流程
- **誰碰得到**:P2 建立 · P3 與 S2 修復 · P4 排程與出貨判定
- **缺什麼**:證據在建立當下被剝除(#3);回不去來源 run / case(#11)

## 可追溯性設計原則

這些原則用來裁決後續每一個介面決定。它們不是功能清單,是**判準**:任何新設計違反其中一條,就退回重想。

### 每一個關聯都要雙向可走

現況的關聯幾乎都是單向可見:A 看得到 B 存在,卻點不過去;或 B 根本不知道 A 的存在。凡是資料層有連結的地方,**兩端都要有可點的入口**。

- **契約 ↔ 需求**:契約要列出需求的名稱與狀態且可點;需求頁的覆蓋率面板每列可點回契約
- **證據 → 缺陷**:已有。**缺陷 → 證據 / 一輪驗證 / 契約**:缺
- **契約 → 歷次驗證**:缺。這是 P1 與 P3 都要的視角

### 證據必須完整跨越交接點

QA 記下的東西,RD 或其 agent 要**原封不動**拿到。任何在交接時剝除資訊的轉換都是缺陷,不是取捨。這條原則直接來自 J4 的失敗模式。

- 實際結果的富文本與附件,要完整帶進缺陷描述
- 附件實體要能同時被結果與缺陷 work item 參照,不是複製兩份

### 人與 agent 同能力

凡人在介面上能做的,MCP 與 CLI 都要能做到同樣完整;凡 agent 寫入的內容,人在介面上都要看得懂並能追溯。這是 S2 存在的前提,也是這套系統相對商業工具的差異點。

- 新增任何介面動作時,同步確認對應的 MCP tool 與 CLI 指令存在且參數等價
- agent 的寫入要留下可辨識的來源,人才能判斷這筆是誰做的

### 深連結是基礎設施,不是功能

每個實體都要有可定址的網址。這是前面三條原則的**技術前提** —— 沒有它,「可點過去」在實作上無從談起。缺口 #11 之所以列為阻擋項,原因就在這裡。

建議的路由結構:

```
/testing                         → 導向 overview
/testing/overview
/testing/cases                   → 可帶 ?folder= 篩選
/testing/cases/:sequence         → 單一契約,需求頁由此連入
/testing/runs
/testing/runs/:runId             → 一輪驗證
/testing/runs/:runId/:runCaseId  → 單一執行項,缺陷由此連回
```

### 不可變性要在介面上被看見

版本化、追加式結果、釘住版本 —— 這些是系統最有價值的保證,但使用者現在幾乎感覺不到。部分已呈現(編輯時會提示將產生新版本、執行時顯示釘住的版本號),但**看不到歷史本身**。

- 契約要能瀏覽版本歷史,並看出哪一版被哪些驗證釘住
- 結果以時間軸呈現每次追加,讓「失敗 → 修復 → 重驗」的歷程可讀

## 第 4 節 · 介面設計

三個介面,對應三個 persona 的關鍵時刻:P1 定義契約、P2 與 P3 交接證據、P4 判斷可否出貨。設計以前述五條原則為判準,並遵守一條額外的總則。

### 總則:優先複用 Plane 自己的互動元件

Testing 之所以感覺像外掛,正是因為它**重新發明了原生已有的原語** —— 需求連結做成一個貼 UUID 的輸入框,而隔壁 work item 的關聯早就有搜尋 modal。以下設計幾乎不需要新元件,只需要把既有的接上來。這同時是最省工與最能讓 testing 讀起來像原生功能的做法。

| 需要的能力                   | Plane 既有元件                                      | 解掉     |
| ---------------------------- | --------------------------------------------------- | -------- |
| 可搜尋的需求選擇器           | `ExistingIssuesListModal`                           | #1       |
| 連結顯示為可點 chip 且可移除 | `IssueRelationSelect` 模式 · `generateWorkItemLink` | #4       |
| 富文本編輯(含貼圖)           | `DescriptionInput`                                  | #2       |
| 附件上傳 / 清單 / 刪除       | `issues/attachment/*`                               | #2       |
| 版本歷史瀏覽                 | `DescriptionVersionsRoot` 模式                      | 契約版本 |
| 疊層詳情與深連結             | `issues/peek-overview/`                             | #11      |

### 介面一 · 契約詳情

> 路由:`/testing/cases/:sequence`

從清單點入開 peek 疊層,可直接以網址進入全頁。兩者共用同一個內容元件,差別只在容器。

版面:標題列(`TC-12` · `v3` · 手動/自動徽章 · 全頁開啟)→ 分頁(契約 / 歷次驗證 / 版本歷史)→ 內容。

| 區塊         | 設計                                                                                                                                                                       | 解掉  |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----- |
| 需求連結     | 「＋ 連結需求」開 `ExistingIssuesListModal` 搜尋選取,不再貼 UUID。已連結者顯示為 chip:識別碼、標題、狀態圓點,整塊可點到 work item,**✕ 可解除**。服務層目前缺 unlink,需補上 | #1 #4 |
| 空狀態       | 「尚未連結需求 —— **未連結的契約不會出現在覆蓋率報表**」。空狀態要說出後果,不只說沒有東西                                                                                  | —     |
| 歷次驗證分頁 | 每列一次執行:一輪驗證名稱(可點)、build、**當時釘住的版本**、結果、執行者、時間。產生過缺陷者顯示缺陷 chip 可點進 work item。這是契約 → 驗證 → 缺陷的回頭路                 | #6    |

### 實作陷阱

**換掉編輯器會打壞既有的鍵盤流。** 執行工作區的 P/F/B/S 快捷鍵目前**只擋 `HTMLInputElement` 與 `HTMLTextAreaElement`**。富文本編輯器是 `contentEditable`,不屬於這兩者 —— 換上去之後,在編輯器裡打字的每一個 p、f、b、s 都會直接送出一筆結果。這是 append-only 的資料,**送出就收不回來**。改動時必須同步擴充焦點判斷,並補一個回歸測試。

**深連結必須先於這三個介面。** 介面一的全頁與 peek、介面二的執行項網址、介面三的每一列連結,全部依賴 #11。沒有路由,這三個設計都只能做半套。實作順序上它不是選項而是前置條件。
