# Project Overview:從功能對齊改成產品戰情室

> 狀態:規格草稿 · 2026-08-03
> 前身:ADR 0005(Overview 的後端)、`testing-product-definition.md`(價值鏈與 persona)

## 為什麼要改

現在的 Overview 來自 enterprise-parity 計畫,所以它報告的是**商業版 Plane 報告的東西** ——
六塊並排的資料,沒有回答任何一個具體問題。

它要服務的其實是兩種人,而兩種人問的是同一串問題:

| 誰       | 問什麼                                      |
| -------- | ------------------------------------------- |
| 管理階層 | 產品開發到哪了?什麼時候能出貨?              |
| 產品經理 | 推進有沒有在規劃上?客戶在抱怨什麼,接住了沒? |

還有一條**跨職能**的要求:前線業務導入時,客戶反映的抱怨要能及時傳到工程團隊。
所以這頁不能只有工程項目 —— 市場、商務、客戶緊急事件都要有位置。

## 設計原則:三類資料,三種互動規則

這是整份規格的骨幹。每一個區塊都必須先歸類,才能決定它長什麼樣。

| 類別       | 定義                    | 互動規則                       | 為什麼                             |
| ---------- | ----------------------- | ------------------------------ | ---------------------------------- |
| **A 衍生** | 從別的資料算出來        | **不可在此編輯**,只能點進源頭  | 讓人改算出來的數字等於製造兩個真相 |
| **B 分流** | 記錄已存在,人改它的狀態 | **一個動作**,不是表單          | 是狀態轉移,不是重新輸入            |
| **C 原創** | 人在這裡產生第一手內容  | **完整 CRUD**:發布、編輯、刪除 | 這裡就是它的家                     |

違反這條規則的設計會出現的症狀:算出來的數字旁邊放一個可編輯欄位,兩者永遠可以互相矛盾
而沒有人負責。現在的 Properties 面板就是這樣被拿掉的。

## 逐區塊:讀哪來、誰寫、寫去哪

| 區塊          | 類  | 讀                                              | 寫                             | 缺                    |
| ------------- | --- | ----------------------------------------------- | ------------------------------ | --------------------- |
| 出貨判定      | A   | `testing/overview` 的 `release_gate`            | 無                             | 已完成                |
| 進度 / 里程碑 | A   | `overview`                                      | 無                             | 已完成                |
| 需要注意      | A   | `Issue.priority` + `target_date`                | 無(點進工作項改)               | 端點 + 畫面           |
| 客戶前線      | B   | `IntakeIssue`(`source`/`source_email`/`status`) | `PATCH intake-issues/<id>/` ✅ | 畫面 + 客戶屬性       |
| 客戶標記      | B   | `WorkItemPropertyValue`                         | `work-item-property-values` ✅ | 屬性要先建            |

**API 的寫入路徑幾乎都在**,缺的是 UI 與一個欄位。

## 需要的 schema 變更:只有一項

### 公佈欄分類 → 掛 Label,不要新 enum

`EntityUpdate.status` 只有 `on_track / at_risk / off_track`,那是**專案健康度**不是主題分類,
不能挪用。

分類必須是**活的** —— 使用者自己增刪,像 Notion。`Label` 已經滿足:每專案獨立、有顏色、
有階層(`parent`)、設定頁現成。

所以只加一張 join table:

```
EntityUpdateLabel(entity_update, label, project, workspace)
```

**結構動一次 migration,分類值永遠由使用者決定。** 沒有任何分類名稱寫進程式碼。

### 客戶 → 用既有的 WorkItemProperty,零 migration

`WorkItemProperty` 已經支援 7 種型別、可綁定特定 work item type、可設必填與預設值。
建三個屬性即可,全部透過現有設定頁:

| 屬性       | 型別                             | 它改變什麼決定                        |
| ---------- | -------------------------------- | ------------------------------------- |
| 客戶       | `multi_select`                   | 哪個客戶在抱怨 → 分組、看單一客戶全貌 |
| 導入階段   | `select`:POC / 試營運 / 正式上線 | 同一個 bug,正式上線客戶回報的先修     |
| 客戶承諾日 | `date`                           | **已存在**;有無對外承諾 → 排程硬約束  |

綁在 Bug 與 Intake 相關的 type 上,不要綁全部 —— 內部技術債不該被問哪個客戶。

專案層而非 workspace 層:專案彼此獨立,同一個客戶若跨專案合作就各自建立。等到跨專案
查詢真的變成需求,再升級成 workspace 實體,那時才會知道要存什麼欄位。

## 分階段

每一階段都可獨立出貨、獨立 revert。

**階段一 · 公佈欄成形**(核心訴求)

1. 公佈欄移到顯眼位置,支援編輯與刪除(API 已具備,`deleteUpdate` 目前是死程式碼)
2. 編輯過的公告顯示「已編輯」—— 公告被默默改掉比不能改更糟
3. 權限:作者本人與 ADMIN
4. `EntityUpdateLabel` + 分類篩選列

**階段二 · 客戶前線**

1. 建三個客戶屬性(設定頁操作,不寫程式)
2. 新端點:依客戶分組的 Intake 摘要(待處理 / 已排入 / 已婉拒)
3. 面板 + 一鍵分流(`PATCH` 狀態,不開表單)

**階段三 · 需要注意**

1. 新端點:逾期與緊急工作項,最多 5 筆
2. 面板,每筆可點進工作項

**階段四 · 收尾**

1. 會議紀錄連到 Pages
2. Activity 收合到底部

## 不做什麼

- **不做跨專案客戶視圖**。專案獨立是前提;跨專案是另一個頁面,等這個模式證明有用再說。
- **不加 CRM 欄位**(聯絡人、合約金額、產業別)。它們不會改變工程接下來做什麼。
  沒人填的欄位比沒有欄位更糟,因為它看起來像資料。
- **不讓 A 類區塊可編輯**。要改就點進源頭改。

## 驗收

- 公佈欄:發布、編輯、刪除、回覆、依分類篩選;非作者非 ADMIN 看不到編輯入口
- 客戶前線:標了客戶的 Intake 會分組;一鍵把待處理改成已排入,列表即時反映
- 需要注意:逾期與緊急各自出現,點擊進入該工作項
- 沒有測試資料的專案不顯示出貨判定;沒有 Intake 的專案不顯示客戶前線
